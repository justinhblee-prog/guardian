# Guardian AdBlock — 라이선스 및 필터 업데이트 운영 설계

작성일: 2026-11-14

이 문서는 Guardian AdBlock의 유료 라이선스 운영과 광고 차단 필터 배포를 함께 운영하기 위한 구현 기준입니다. 현재 구현된 기능과 추가 개발 항목을 구분합니다.

## 1. 필터 업데이트 — 현재 구현과 다음 보강

### 현재 소스에서 확인된 기능
- Android WorkManager 고유 주기 작업으로 네트워크 연결 시 필터를 갱신합니다.
- 설정 주기: 6시간 / 12시간 / 24시간 / 7일. 자동 업데이트를 끄면 예약 작업을 취소합니다.
- 앱 실행 시 만료된 목록을 확인하고, 필터 화면에서 수동 업데이트를 실행할 수 있습니다.
- 기본 광고 필터, 선택형 보안 필터, Android 광고 SDK 필터를 개별 관리합니다.
- HTTPS 다운로드, 리디렉션 제한, 다운로드 크기 제한(10MB), 파싱 후 최소 유효 규칙 수 검증을 수행합니다.
- 임시 파일을 검증한 뒤 원자적으로 교체하고, 실패 시 기존 정상 캐시를 보존합니다.
- 캐시 교체 시 직전 정상 파일을 백업으로 유지합니다. 파일 교체 또는 메타데이터 저장이 실패하면 이전 캐시를 복구하며, 프로세스가 교체 도중 종료된 경우 다음 캐시 확인 시 백업을 복구합니다.
- 업데이트 후 보호 중인 VPN 서비스에 규칙 재적용을 요청합니다.
- 업데이트 중 선택 옵션 변경을 잠가 다운로드 스냅샷과 실제 설정이 달라지는 문제를 막습니다.

### 추가 구현 기준
1. 앱이 직접 관리하는 HTTPS manifest를 도입합니다. manifest에는 manifestVersion, generatedAt, sourceId, sourceVersion, URL, SHA-256, 최소 유효 규칙 수, 필터 유형을 기록합니다.
2. manifest와 각 필터의 SHA-256을 검증하고, Android 최소 지원 버전(API 26)과 호환되는 SHA256withRSA 공개키로 manifest 서명을 검증합니다. 검증기는 RSA 2048비트 이상, 서명 일치, 필수/중복 항목, HTTPS URL, SHA-256 형식, 생성 시각의 미래 오차(10분 이내), 저장된 마지막 manifest 시각보다 새로운 버전인지 검사합니다. 소스별 마지막 승인 시각을 앱 내부 파일에 원자적으로 저장하는 ManifestTimestampStore와 재시작 후 유지·오래된/동일 시각 거부·손상 데이터 fail-closed 회귀 테스트도 추가했습니다. 이 검증기는 선택적 운영 설정이 제공될 때 FilterListManager의 실제 업데이트 경로에서 사용됩니다. 운영 서버·공개키 고정과 실제 서버 end-to-end 검증은 아직 남아 있습니다. 캐시 파일 교체/메타데이터 저장 실패에 대한 백업 복구와 JVM 회귀 테스트도 추가했습니다. 서명 개인키는 서버 Secret Manager에만 둡니다.
3. 다운로드 → 크기/해시/서명/파싱 검증 → 임시 캐시 → 원자적 교체 순서를 지킵니다. 하나라도 실패하면 마지막 정상 캐시를 유지합니다.
4. 필터별 버전·해시·규칙 수·마지막 성공 시각·마지막 오류를 앱 화면에 표시합니다.
5. 수동 업데이트 버튼, 전체 업데이트, 필터별 업데이트, Wi-Fi 전용 옵션, 업데이트 기록을 제공합니다.
6. 업데이트 서버 장애 시 현재 필터로 계속 보호하고, 새 설치에서 정상 필터가 없으면 보호 준비 상태를 명확히 표시합니다.
7. 필터 긴급 롤백은 manifest의 이전 정상 버전을 재배포해 수행하며, 앱 업데이트 없이 규칙을 교체할 수 있게 합니다.

### 업데이트 정책
- 기본값: 자동 업데이트 켬, 12시간 주기 권장.
- 네트워크가 없으면 대기하고 연결 후 재시도합니다.
- 실패 재시도는 지수형 backoff를 사용합니다.
- 앱이 사용하는 필터 소스와 라이선스 상태는 분리합니다. 라이선스 서버 장애가 광고 차단 엔진이나 기존 필터를 중지시키면 안 됩니다.

## 2. 라이선스 — 서버 기반 발급/인증

### 상품 정책(초안)
- Free: 기본 DNS 광고/추적 필터, 기본 업데이트.
- Pro: 추가 프리미엄 필터, 고급 정책, 확장 설정.
- Lifetime: 결제 1회, 정책에 명시된 영구 Pro entitlement.
- 가격, 세금, 환불, 구독 기간, 동시 활성화 기기 수는 판매 시작 전에 운영자가 확정합니다.

### 구성 요소
- Android 앱: 라이선스 키 입력, 상태 조회, 기기 활성화/비활성화, 구매 복원 UI.
- License API: 발급, 활성화, 갱신, 취소, 기기 제한, 관리자 발급/정지.
- DB: 라이선스 해시, 상품/권한, 만료, 활성화 기기, 결제 참조, 감사 이벤트.
- Admin console: 키 생성, 고객 연결, 활성화 초기화, 정지/취소, 이력 조회.
- 결제 제공자: 초기에는 수동 발급/외부 결제 확인으로 시작할 수 있고, 이후 Google Play Billing 및 웹 결제를 각각 검증합니다.

### API 계약 초안
- POST /v1/licenses/activate — 키 + 앱 설치별 임의 deviceId를 보내 활성화.
- POST /v1/licenses/refresh — 현재 기기의 권한 토큰 갱신.
- POST /v1/licenses/deactivate — 현재 기기 등록 해제.
- GET /v1/licenses/status — Free/Pro/Lifetime, 만료 및 기기 한도 확인.
- 관리자 전용 POST /v1/admin/licenses — 라이선스 발급.
- 관리자 전용 POST /v1/admin/licenses/{id}/revoke — 취소/정지.

모든 요청은 TLS와 서버 측 입력 검증을 사용합니다. 라이선스 키 원문은 발급 시 한 번만 보여주고 DB에는 Argon2id 등으로 해시한 값만 저장합니다. 앱은 Android ID나 광고 ID를 기기 식별자로 쓰지 않고, 앱 설치 시 생성한 무작위 UUID를 사용합니다.

### 인증 토큰과 오프라인 정책
- 서버는 RSA-2048/SHA-256 개인키로 짧은 수명의 entitlement token을 서명하고, 앱에는 공개키만 포함합니다.
- 토큰에는 product, entitlement, issuedAt, expiresAt, licenseId의 비식별 참조, device binding을 포함합니다.
- 기본 온라인 갱신 간격은 24시간, 오프라인 유예는 최대 72시간을 초기 제안값으로 둡니다. 실제 판매 정책 확정 후 조정합니다.
- 토큰 만료/서버 장애 시 Pro 권한만 Free로 낮추며 DNS 보호 자체를 강제로 끄지 않습니다.
- 앱에 라이선스 발급용 비밀키, 서버 개인키, 관리자 API 키를 포함하지 않습니다.

### 결제·발급 원칙
- Google Play 배포 시 디지털 기능 판매는 Google Play Billing 정책을 우선 확인하고 해당 결제 흐름을 구현합니다.
- 웹 결제를 추가하더라도 서버가 결제 제공자 webhook을 검증한 뒤 entitlement를 부여합니다. 앱의 클라이언트 응답만 믿고 Pro를 활성화하지 않습니다.
- 환불/차지백/구독 취소는 webhook과 서버 상태 동기화로 권한을 갱신합니다.
- Lifetime은 '영구'의 범위, 앱 지원 기간, 기기 변경, 환불 조건을 약관에 명시합니다.

## 3. 데이터 모델 초안
- products(id, code, name, entitlement_json, active)
- licenses(id, key_hash, product_id, status, expires_at, max_devices, created_at, revoked_at)
- activations(id, license_id, device_id_hash, app_version, activated_at, last_seen_at, deactivated_at)
- purchases(id, provider, provider_transaction_id, license_id, status, verified_at)
- license_events(id, license_id, event_type, actor, metadata_json, created_at)

키·토큰·결제 식별정보는 로그에 원문을 남기지 않습니다. 관리자 작업은 모두 감사 이벤트로 기록합니다.

## 4. 구현 순서
1. 필터 업데이트: 현재 WorkManager/캐시 구조의 회귀 테스트와 실패 복구 검증을 마무리합니다.
2. 필터 manifest: 스키마, SHA-256, RSA-2048/SHA-256 서명 검증기와 테스트 벡터를 추가합니다.
3. 필터 UI: 버전/해시/갱신 시각/오류 및 지금 업데이트 동작을 연결합니다.
4. 라이선스 API: DB 마이그레이션, 관리자 발급, activate/refresh/deactivate/status API를 구현합니다.
5. 앱 라이선스 UI: Free/Pro 상태, 키 입력, 기기 관리, 복원, 오류/오프라인 상태를 연결합니다.
6. 결제 연동: 배포 경로에 맞는 Google Play Billing 및 서버 검증을 추가합니다.
7. 테스트: 만료, 취소, 중복 활성화, 기기 한도, 서버 장애, 토큰 위조/만료, 오프라인 유예, 결제 환불, 필터 서명 실패/롤백을 회귀 테스트합니다.

## 5. 현재 미완료 경계
- 앱에는 서버 발급 Pro entitlement 토큰의 RSA-2048 이상/SHA256 서명 검증기가 추가되었습니다. 정확한 원문 payload 서명, 토큰 버전·상품·권한·발급/만료 시각·기기 바인딩·라이선스 참조를 검증하며 위조, 만료, 미래 발급, 다른 기기 바인딩, 약한 공개키를 거부합니다. JVM 회귀 테스트가 추가되었습니다. 다만 이 검증기는 아직 앱의 권한/UI 흐름에 연결되지 않았고 운영 공개키도 고정되지 않았습니다.\n- 라이선스 서버/API/관리자 콘솔/결제 검증은 아직 구현되어 있지 않습니다. 이 문서는 구현 계약이며 실제 발급 가능한 서비스가 아닙니다.
- 서명 manifest가 승인되면 필터별 sourceVersion, SHA-256, generatedAt을 캐시 메타데이터와 함께 저장하고, 캐시 교체가 실패하면 이전 메타데이터로 복구합니다. 필터 상태 화면에는 승인된 서명 버전·해시 앞부분·생성 시각을 표시합니다.
- Guardian 서명 manifest 다운로드 경로를 추가했습니다. `GUARDIAN_MANIFEST_BASE_URL`과 `GUARDIAN_MANIFEST_PUBLIC_KEY`(또는 동등한 Gradle properties)를 함께 설정하면 앱은 `{baseUrl}/{sourceId}.manifest`를 조회하고 `X-Guardian-Signature` 헤더의 RSA-2048/SHA-256 서명을 검증한 뒤, manifest의 HTTPS 필터 URL에서 내려받은 콘텐츠의 SHA-256과 최소 규칙 수를 검사하고 캐시를 교체합니다. 마지막 승인 `generatedAt`은 소스별로 앱 내부 파일에 저장하며 캐시/메타데이터 교체 실패 시 이전 시각도 복구합니다. 둘 다 비어 있으면 기존 커뮤니티 필터 직접 다운로드 경로를 유지하고, 하나만 설정되면 업데이트를 거부합니다. 따라서 실제 운영 서버·공개키 배포는 아직 미구성이고, 서버 연동 end-to-end 검증도 남아 있습니다.
- 실제 운영 도메인, 서버 계정, 결제 계정 및 production 서명키는 아직 구성되지 않았습니다. 비밀키를 Git 저장소나 채팅에 입력하지 않습니다.

### Android 앱 통합 진행 사항
- 앱 설치별 무작위 UUID를 생성하고 SHA-256 기기 바인딩 값으로 변환합니다. Android ID·광고 ID는 사용하지 않습니다.
- 서버 서명 entitlement를 저장하기 전에 RSA 서명, 상품/권한, 발급·만료 시각 및 현재 설치 기기 바인딩을 검증합니다. 저장된 토큰도 앱 설정 화면을 표시할 때마다 다시 검증하며 만료·위조·다른 설치 토큰은 Pro 권한에서 제외합니다.
- 공개키는 `GUARDIAN_LICENSE_PUBLIC_KEY` 환경 변수 또는 `guardianLicensePublicKey` Gradle 속성으로 빌드 시 주입하도록 연결했습니다. 실제 운영 공개키가 비어 있으면 Pro 라이선스는 활성화되지 않습니다.
- 설정 화면은 검증된 Pro 토큰이 있을 때만 PRO로 표시하고, 그 외에는 FREE로 표시합니다. DNS 보호 기능은 라이선스 상태와 독립적으로 유지됩니다.
- 아직 라이선스 활성화 API 호출/키 입력 UI/관리자 콘솔/결제 검증은 연결되지 않았습니다. 따라서 이 단계는 검증된 토큰의 기기 종속 저장·재검증 기반이며, 사용자 라이선스 발급/활성화 서비스가 완성된 것은 아닙니다.
